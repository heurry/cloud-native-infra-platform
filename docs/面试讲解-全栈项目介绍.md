## 0. 先背下来：电梯演讲

**一句话**：这是一个面向中文客服的**云原生大模型训练微调、推理优化与 AIOps 实验平台**，把训练任务编排、vLLM 服务启停、可复现压测、Profiler 归因和故障诊断做成统一控制面。

**30 秒版**：
> 我做了一个全栈的云原生大模型实验平台。后端是 Go 控制面，对接 Postgres、Redis、MinIO、Kubernetes 和本机 Agent，前端是 React + TypeScript。训练侧用 Kubeflow `PyTorchJob` 编排 Qwen3.5-4B LoRA；推理侧在双 RTX 3090 上运行 Qwen3.6-27B-FP8，通过 OpenAI-Compatible API 做 1K/2K、1--16 并发压测，采集 TTFT、TPOT、P95、吞吐、正确性和显存。平台还能从 benchmark、Profiler、vLLM 日志、GPU 与 K8s 证据生成 AIOps 根因和处理建议。

**2 分钟版**（加这些）：
- 数据流：浏览器 → nginx 反代 → Go 控制面（一条中间件链：请求ID、链路追踪、限流、幂等、认证授权）→ handler → store 层 → Postgres/Redis/MinIO/K8s。
- 推理优化：DianJin 客服共享前缀矩阵中，prefix caching 平均 TTFT 降低 70.4%、TPOT 降低 44.4%；调度公平复测形成 `8/4096` 均衡档和 `16/8192` 高并发 TTFT/吞吐档。
- Profiling：PyTorch Profiler 显示 NCCL ring all-reduce 和 Marlin FP8 GEMM 是主要 Self CUDA 开销，说明瓶颈是双卡 PCIe 通信与 3090 非原生 FP8，而不是 FlashAttention。
- AI 能力：Go 负责编排和取证，把 benchmark、训练任务、GPU、K8s 与日志证据喂给 Python AI 服务；AIOps 先走确定性质量/稳定性门禁，再做 scheduler、prefill、decode、显存或训练故障归因。
- RAG：项目保留知识库能力，但不是本轮训练和推理优化的依赖，面试时不要把它讲成主线。
- 工程化：OpenTelemetry 全链路追踪 + Prometheus/Grafana 指标；分层测试（单元/集成/混沌/负载/e2e）；Docker 多阶段构建 + Helm chart 可自托管。

## 1. 这个项目到底是什么

### 1.1 它不是模型，是"管模型的平台"
很多人简历写"我部署了一个大模型"。这个项目高一个层次：它是**管理那套部署的控制平面（Control Plane）**。
类比你熟的东西：vLLM 是"发动机"，这个平台是"整辆车的仪表盘 + 中控 + 自动驾驶辅助"——你不直接碰发动机，而是通过平台去注册、发布、观测、诊断、扩缩容、训练。

### 1.2 它解决什么问题（面试可讲的"动机"）
一套生产级模型服务，工程上要回答一堆问题：
- 模型有哪些版本？谁在 serve？血缘是什么？→ **模型注册中心**
- 配置（限流阈值、网关参数）怎么改、怎么回滚、谁改的？→ **配置中心 + 审计**
- 线上指标（QPS / P95 延迟 / TTFT / GPU 利用率）怎么看？告警怎么来？→ **可观测**
- 出问题了根因是什么？→ **AI 智能诊断**
- 怎么不停机发新版本？坏了怎么自动回滚？→ **CI/CD 滚动发布**
- 流量涨了怎么自动加副本？→ **弹性扩缩容 HPA**
- 怎么灰度新模型 / A-B / 影子流量？→ **模型路由**
- 怎么基于反馈做微调训练，训完自动注册回平台？→ **Kubeflow 分布式训练**（最新）

### 1.3 诚实定位（很重要，面试别吹过头）
这是**作品集/演示级**项目，不是有真实用户的生产系统。但它的关键差异化是：**绝大多数能力是"真执行"而不是"假数据演示"**——CI/CD 真的改 K8s Deployment 镜像并轮询滚动发布、扩缩容真的调 K8s API、存储归档真的把 Postgres 数据搬进 MinIO。面试时这个"真"字是最大的加分点，要主动强调，并诚实标注哪些是"建模/只读"。

### 2.2 一次普通请求的旅程（务必能口述）
以"前端打开配置中心列表"为例：
1. 浏览器发 `GET /api/configs`，nginx 同源反代到 Go 控制面。
2. **中间件链**依次过：生成 request-id → 开一个 OTel span（链路追踪）→ Redis 令牌桶限流检查 → （写请求才查）幂等键 → 解析 JWT 看身份 → RBAC 看权限。
3. handler 调 **store 层**（领域逻辑），store 用 **sqlc 生成的类型安全查询** 走 pgx 连接池查 Postgres。
4. 可能先查 **Redis 缓存**（cache-aside：命中直接返回，没命中查库再回填）。
5. 返回统一 JSON 信封；出错则 `{code, message, requestId}`。
6. 前端用 **react-query** 收数据、缓存、按 10s 轮询刷新。

### 2.3 一次 AI 诊断的旅程（你的强项，重点讲）
"Agent 诊断"按钮：
1. 前端 `POST /api/ai/diagnose:agent`。
2. Go 的 **agent 编排循环**（最多 5 步）开始：调 Python AI 服务的 `/internal/agent-step` 问"下一步该查什么工具 / 还是给结论"。
3. AI 服务让 **vLLM 上的 Qwen3-4B 发起结构化工具调用**（vLLM 开了 `--enable-auto-tool-choice --tool-call-parser qwen3_coder`）。
4. Go 本地执行只读取证工具：`recent_metrics` / `recent_deployments` / `open_incidents` / `kubernetes_pods`，把结果回灌给模型。
5. 多轮后模型给出根因 + 建议动作；Go 把**完整推理轨迹**落库 + 审计，前端展示"模型查了哪些证据"。
6. 没 GPU 时走确定性 stub 脚本，降级但契约一致——**降级诚实**是这个项目反复出现的设计原则。

## 3. 技术栈逐项扫盲

> 每项讲清三件事：**是什么 → 为什么用 → 本项目怎么用**。面试官最爱问"为什么选 X 不选 Y"。

### 3.1 后端：Go 语言 + 控制面
- **是什么**：Go（Golang）是 Google 出的编译型语言，语法简单、自带并发（goroutine）、编译成单个静态二进制。
- **为什么用**：云原生基础设施的事实标准语言——Kubernetes、Docker、Prometheus 全是 Go 写的。优点：①并发模型简单（一个 `go f()` 就起一个轻量协程）；②单二进制部署，没有运行时依赖；③性能接近 C 但开发效率高；④官方 K8s 客户端 client-go 是 Go 的。
- **本项目怎么用**：
  - **单一后端入口**：以前是 Java + Python 多后端，迁移成了 Go 单体控制面（更简单、更快）。
  - **chi 路由**：一个轻量 HTTP 路由库，把 URL 映射到处理函数。
  - **goroutine 跑后台任务**：比如 CI/CD 滚动发布、训练任务，提交后起一个 goroutine 异步轮询 K8s 状态、回写数据库——请求立刻返回，不阻塞。
  - **分层架构**：`handler（HTTP层）→ store（领域/业务逻辑层）→ sqlc/pgx（数据访问层）`。这是后端经典三层，面试常考"为什么分层"——答：关注点分离、可测试、可替换底层。

**面试高频**：
- *Go 的并发为什么好？* → goroutine 是用户态轻量线程（几 KB 栈），调度由 Go runtime 管，能轻松开几十万个；线程间用 channel 通信（"不要用共享内存通信，要用通信共享内存"）。
- *Go 为什么适合微服务/云原生？* → 单二进制 + 启动快 + 内存占用低 + 静态编译进极小的 distroless 镜像。

### 3.2 前端：React + TypeScript + Vite
- **是什么**：
  - **React**：Facebook 出的前端框架，核心思想是"UI = 组件函数(状态)"，状态变了自动重渲染。
  - **TypeScript（TS）**：给 JavaScript 加了静态类型，编译期就能抓住类型错误。
  - **Vite**：现代前端构建工具，开发时热更新极快，打包出静态文件（HTML/JS/CSS）。
  - **SPA（单页应用）**：整个站只有一个 HTML，页面切换靠前端 JS 路由，不刷新整页。
- **为什么用**：React 是业界主流、生态最大；TS 在大型项目里几乎必备（类型即文档，重构安全）；Vite 比老的 webpack 快很多。
- **本项目怎么用**：
  - ~16 个页面（总览/服务/K8s/配置/流水线/可观测/AIOps/知识库/模型注册/路由/存储/训练…）。
  - **react-query**：管理"从后端取数据"这件事——自动缓存、自动轮询刷新、加载/错误态。比手写 fetch 优雅得多。
  - **SSE 客户端**：聊天和诊断是流式输出（一个字一个字蹦），用 Server-Sent Events 协议。
  - **结构约定**（项目自己的规矩）：页面只做"组装"，逻辑抽到 `lib/use*.ts` 钩子，视图组件放 `components/<功能>/`，类型放 `types/<功能>.ts`。面试可讲"我有清晰的前端分层约定"。
  - **打包后用 nginx 托管**，nginx 把 `/api` 反代到 Go 后端（同源，规避跨域 CORS 问题）。

**面试高频**：
- *什么是组件化？* → 把 UI 拆成可复用的小积木（按钮、表格、抽屉），每个管自己的状态和渲染。
- *前端怎么和后端通信？* → 主要 REST/JSON（`fetch`），流式场景用 SSE；本项目还有 JWT 放在 `Authorization` 头里。
- *为什么要 TypeScript？* → 类型安全、IDE 自动补全、重构不怕漏、类型就是契约文档。

### 3.3 数据库三件套：Postgres / Redis / MinIO
这三个是"分层存储"的核心，面试常考"什么数据放哪、为什么"。

#### Postgres（关系型数据库，主存储）
- **是什么**：最强的开源关系型数据库（RDBMS）。数据存在**表**里（行 + 列），用 **SQL** 查询，支持**事务**（ACID：原子性/一致性/隔离性/持久性）。
- **为什么用**：需要强一致、关联查询、事务的结构化数据就用它——配置项、模型版本、部署记录、审计日志、训练任务都在这。
- **本项目怎么用**：
  - **迁移（migration）**：用 golang-migrate，把建表/改表写成有版本号的 SQL 文件（000001…000012），程序启动自动按顺序执行。好处：DB schema 可版本控制、可重放、团队一致。
  - **sqlc**：把 SQL 查询编译成**类型安全的 Go 代码**——你写 SQL，它生成对应的 Go 函数和结构体，编译期就能发现字段对不上。比手写拼 SQL 安全。
  - **pgx**：Go 的 Postgres 驱动 + 连接池。
  - **pgvector**：Postgres 的向量扩展，能存 embedding 向量并做相似度检索——**这就是 RAG 的检索底座**（不用单独上 Pinecone/Milvus）。
- **必懂概念**：
  - **事务**：一组操作要么全成功要么全回滚。本项目存储归档时用事务：先传 MinIO 成功，再在事务里删 Postgres 行 + 写归档清单，保证不会"删了但没备份"。
  - **索引**：加速查询的数据结构（如训练任务表按 `created_at` 建索引）。
  - **连接池**：复用数据库连接，避免每次请求新建连接的开销。

#### Redis（内存数据库，缓存/热数据）
- **是什么**：基于内存的键值（KV）数据库，极快（微秒级），数据结构丰富（string/hash/list/set/zset）。
- **为什么用**：内存所以快，适合**缓存**、**限流计数**、**会话**、**热数据**。代价是容量受内存限制、持久化弱。
- **本项目怎么用**：
  - **缓存（cache-aside 模式）**：读请求先查 Redis，命中直接返回（快），没命中查 Postgres 再写回 Redis。
  - **令牌桶限流**：用 Redis 原子操作实现分布式限流（每个 IP/用户每秒多少请求）。
  - **幂等键**：写请求带个幂等键存 Redis，重复提交直接返回上次结果，防止重复执行。
  - **降级**：Redis 挂了不影响主流程——缓存穿透到 DB、限流放行、幂等重新执行（这叫 **fail-open**）。

#### MinIO（对象存储，S3 兼容）
- **是什么**：开源的对象存储，兼容 AWS S3 API。存的是"对象"（文件 + 元数据），用 key 取，适合大文件、非结构化数据。
- **为什么用**：模型产物（LoRA adapter、checkpoint）、冷归档数据这类大对象不该塞进数据库——对象存储便宜、能存海量、有预签名 URL 直接下载。
- **本项目怎么用**：
  - 模型注册中心上传**模型产物**到 MinIO，给**预签名下载链接**（临时有效的直下 URL）。
  - **冷归档**：存储归档器把 Postgres 里过期的指标/审计数据序列化成 NDJSON 上传 MinIO，再从 Postgres 删除——**热数据在 PG、冷数据在 MinIO**，这就是"分层存储生命周期"。
  - 训练产出的 LoRA adapter 也写 MinIO（key 经 `OUTPUT_URI` 注入训练容器）。

**一句话记忆**：**Postgres = 结构化强一致主存储；Redis = 快的临时热数据；MinIO = 大文件/冷数据对象库。**

### 3.4 云原生：容器 / Kubernetes / Helm
这是项目的"云原生"招牌，也是你最不熟、最该补的部分。

#### 容器 / Docker
- **是什么**：容器把"应用 + 它的所有依赖"打包成一个可移植的**镜像（image）**，到处都能一致地跑。比虚拟机轻量（共享内核）。
- **本项目怎么用**：
  - **多阶段构建（multi-stage build）**：Go 服务的 Dockerfile 第一阶段用 `golang:1.22` 编译，第二阶段把编译好的二进制拷进 `distroless/static` 极小镜像——**最终镜像几 MB、无 shell、攻击面小**。这是面试加分点。
  - 前端：node 镜像构建 → nginx 镜像托管。
  - 本机没装 Go，所有 Go 编译/测试都在 `golang:1.22` 容器里跑（`docker run ... golang:1.22 go build`）。

#### Kubernetes（K8s，容器编排）
- **是什么**：管理大规模容器的"操作系统"。你声明"我想要 3 个副本",K8s 持续保证现实符合声明（**声明式 + 调和循环 reconciliation**）。
- **核心概念**（必背）：
  - **Pod**：最小调度单位，一个或多个容器的组合。
  - **Deployment**：管理一组同样的 Pod（副本数、滚动更新、回滚）。
  - **Service**：给一组 Pod 一个稳定的网络入口（负载均衡）。
  - **Namespace**：逻辑隔离的"分区"（如 `aibrix-system`、`training`、`default`）。
  - **HPA（HorizontalPodAutoscaler）**：按 CPU/指标自动增减副本数。
  - **滚动更新（rolling update）**：逐个替换 Pod 升级，不停机；失败可回滚。
  - **minikube**：本地单机版 K8s，用来开发测试。
- **本项目怎么用**（重点，因为是"真执行"）：
  - **client-go**：K8s 官方 Go 客户端。Go 控制面直接连 K8s API。
  - **读**：列 pods/deployments/events/nodes/HPA，做可观测快照；还能经 API server 代理抓 vLLM Pod 的 `/metrics`。
  - **写**：
    - CI/CD：`PatchDeploymentImage` 改 Deployment 镜像 + `RolloutStatus` 轮询滚动发布，失败自动回滚到旧镜像。
    - 扩缩容：`ScaleDeployment`（改副本数）、`UpsertHPA`/`DeleteHPA`（配/删自动伸缩）。
    - 训练：用 **dynamic client** 操作 Kubeflow 的 `PyTorchJob` 自定义资源（CRD）。
    - 日志：`PodLogs` 拉训练 Pod 日志。
  - **安全护栏**（面试重点讲）：所有 K8s 写操作受三重保护——①`ALLOW_K8S_WRITES`/`ALLOW_TRAINING` feature flag（默认关）；②命名空间允许名单；③serving 命名空间（aibrix/vllm/qwen/envoy）**硬禁**——防止平台误伤正在跑的推理栈。**集群不可达时优雅降级**（`available=false`，绝不编造数据、不阻塞启动）。

#### Helm
- **是什么**：K8s 的"包管理器"，把一堆 K8s YAML 模板化 + 参数化，一条 `helm install` 部署整套应用。
- **本项目怎么用**：有一个 Helm chart 能把整个平台（go-server/web/postgres/redis/minio/agent）一键装进 K8s，支持多副本、ingress、各种安全默认配置。

#### Kubeflow（机器学习平台 / 分布式训练）
- **是什么**：跑在 K8s 上的 ML 工具集。本项目只用了它的 **Training Operator**——它定义了 `PyTorchJob` 这种自定义资源（CRD），能把一个 PyTorch 训练拆成 master + N 个 worker，自动做**分布式数据并行（DDP）**。
- **本项目怎么用**（Phase F，最新）：
  - 用户在平台提交训练任务 → Go 建数据库台账（pending）→ 起 runner goroutine → 用 dynamic client 创建 `PyTorchJob` → 轮询相位（Created/Running/Succeeded/Failed）写回进度 → **成功后自动把训练出的 LoRA adapter 注册进模型注册中心**（血缘指回基座模型）——形成"训练 → 注册 → 可服务"的闭环。
- **你的强项接口**：这块和你懂的 LoRA/微调/分布式训练直接相关，面试可以从这里切进去再往平台外扩。

### 3.5 AI 服务 + Serving + 模型
- **vLLM**（你熟）：高吞吐 LLM 推理引擎（PagedAttention、连续批处理）。本项目跑 **Qwen3-4B AWQ 量化 + LoRA**，多副本。
- **AIBrix**（你可能不熟）：字节开源的"vLLM 的 K8s 原生服务化框架"——提供网关、路由（如按 KV-cache 命中路由）、多副本管理。本项目的指标就来自这套真实 serving 栈。
- **Python AI 服务（FastAPI）**：
  - **是什么**：FastAPI 是 Python 的现代异步 Web 框架，写 API 很快，自带数据校验（Pydantic）。
  - **角色**：当"大模型推理的代理 + RAG 引擎 + agent reasoner"。Go 负责编排和数据，Python 负责跟 LLM 打交道。为什么分开？——Python 的 LLM 生态成熟（openai 客户端、检索库），Go 负责高并发控制面，各干各擅长的。
  - **RAG**：语料 = 平台自己的压测日志，embedding 存 pgvector，检索 + 流式问答 + 反馈回流（被赞的答案回流成评测集 + 重排信号）。

### 3.6 可观测性（Observability）
现代系统的"三大支柱"：**指标（Metrics）、日志（Logs）、链路追踪（Traces）**。
- **Prometheus**：拉取式的指标监控系统，Go 控制面暴露 `/metrics`（请求数、延迟直方图）。
- **Grafana**：把 Prometheus 指标画成仪表盘。
- **OpenTelemetry（OTel）**：厂商中立的可观测标准。本项目用它做**分布式链路追踪**——一个请求从 Go → Python AI 服务 → vLLM，靠 W3C `traceparent` 头串起来，能看到一条跨服务的"瀑布图"（每段耗时多少）。
- **Tempo**：存储/查询链路追踪数据。
- **亮点**：项目还从 OTel span 派生出**实时服务调用图**（连线粗细 = 真实 QPS）。

**面试高频**：*指标和链路追踪区别？* → 指标是聚合数字（QPS、P95），看"系统整体健康"；链路追踪是单个请求的完整路径，看"这一次慢在哪一段"。

### 3.7 横切关注点（每个都是面试题）
- **认证（Authentication）vs 授权（Authorization）**：认证=你是谁（JWT 登录），授权=你能做什么（RBAC 角色）。本项目用 **HS256 JWT**（无第三方库，标准库实现）+ 三级角色 **viewer < operator < admin**：读需登录、写需 operator+。默认关闭（演示零摩擦），开启即门禁，审计绑真实身份。
- **限流（Rate Limiting）**：Redis 令牌桶，防止被打爆。
- **幂等（Idempotency）**：写请求带幂等键，重复提交不重复执行（防网络重试导致重复下单式的问题）。
- **审计日志（Audit Log）**：每个写操作记一条"谁在何时对什么做了什么"，落 Postgres。
- **统一错误信封**：所有错误返回 `{code, message, requestId}`，前端好处理、出问题能按 requestId 追链路。
- **优雅降级（Graceful Degradation）**：**这是全项目的灵魂**。Redis/MinIO/K8s/AI 任一不可用，系统不崩，相关功能降级 + 诚实标注，绝不编造数据。面试一定要讲这个设计哲学。

## 3+. 深入：用本项目真实代码看每一层怎么跑

> 上面是"是什么/为什么"。这一节用**项目里真实存在的代码**把"怎么跑"走一遍。看完你能对着代码讲机制，而不是背定义。
> 全程用一个例子串起来：**用户在前端点"提交训练任务"**，看这一次请求怎么穿过前端 → 后端中间件 → handler → 数据库 → K8s，再流式回到前端。

### A. 一次请求的完整代码走读（提交训练任务）

#### 第 1 站：前端发请求（React hook → fetch）
真实代码 `apps/web/src/lib/useTraining.ts`：
```ts
export function useTraining() {
  const qc = useQueryClient();
  // 列表：每 5 秒自动重新拉一次（轮询），所以提交后进度会自动刷新
  const jobs = useQuery({
    queryKey: ["training", "jobs"],
    queryFn: listTrainingJobs,          // 实际就是 GET /api/training/jobs
    refetchInterval: 5000,
  });
  // 提交：一个"变更"操作
  const submit = useMutation({
    mutationFn: (input) => submitTrainingJob(input),  // POST /api/training/jobs
    onSuccess: (res) => {
      toast.success(`训练任务已提交：${res.name}`);
      qc.invalidateQueries({ queryKey: ["training", "jobs"] }); // 让列表立刻重拉
    },
  });
  return { jobs, submit, cancel };
}
```
**机制讲清楚**：
- `useQuery` = "我要读这个数据"。react-query 帮你管：缓存、加载中/出错状态、按 `refetchInterval` 轮询。你不用手写 setInterval + setState。
- `useMutation` = "我要改数据"。成功后 `invalidateQueries` 把列表标记为"脏"，react-query 立刻重新拉一次 → UI 自动更新。**这就是"状态驱动 UI"**：你不手动操作 DOM，只改数据，React 自动重渲染。
- `submitTrainingJob` 底层就是一个 `fetch("/api/training/jobs", {method:"POST", body: JSON, headers:{Authorization: Bearer <jwt>}})`，nginx 把 `/api` 同源反代到 Go 后端。

#### 第 2 站：穿过中间件链（Go 后端，真实顺序）
真实代码 `server/internal/httpx/router.go`，请求按这个顺序被层层包裹：
```go
r.Use(RequestID)      // 1. 给这次请求生成唯一 id，贯穿日志/错误/链路
r.Use(Telemetry)      // 2. 开一个 OTel 追踪 span + 记 Prometheus 指标（延迟/状态码）
r.Use(Logger)         // 3. 打访问日志
r.Use(Recoverer)      // 4. 兜底 panic，转成 500 而不是整个进程崩
r.Use(cors.Handler()) // 5. 跨域策略
r.Route("/api", func(r chi.Router) {
    r.Use(a.RateLimit())   // 6. Redis 令牌桶限流（超了返回 429）
    r.Use(a.Idempotency()) // 7. 幂等：带 Idempotency-Key 的重复 POST 直接返回上次结果
    r.Use(a.Authn)         // 8. 解析 JWT → 把"你是谁"放进 context
    r.Use(a.Authz)         // 9. 看角色够不够（写操作需 operator+），不够返回 403
    ...
})
```
**机制讲清楚**：中间件 = **洋葱模型**。请求从外层往里穿（1→9），响应再从里往外穿回来。每层只管一件事，互不耦合。这就是为什么"加一个限流"不用动任何 handler——只在链上插一层。
**关键加分点**：每个依赖型中间件都能**降级**——Redis 挂了，限流和幂等"透明直通"（放行），不会因为 Redis 挂了整站不可用（fail-open）。

#### 第 3 站：handler（HTTP 层——校验 + 守卫 + 编排）
真实代码 `server/internal/httpx/training_handlers.go`（精简）：
```go
func (a *API) submitTrainingJob(w http.ResponseWriter, r *http.Request) {
    var req submitTrainingReq
    decodeBody(r, &req)                       // 解析 JSON 请求体

    // ① 参数校验：名字/基座/镜像必填，worker/GPU 数有上限（防误配打爆集群）
    if req.Name == "" || req.BaseModel == "" || req.Image == "" {
        a.badRequest(w, r, "name, base_model, image are required"); return
    }
    // ② 安全守卫：feature flag + 命名空间允许名单 + serving 命名空间硬禁
    if !a.trainingWriteGuard(w, r, namespace, req.Name) { return }

    operator := a.actor(r, req.Operator)      // 从 JWT 拿真实身份（审计用）

    // ③ 落库：建一条 pending 台账，拿到 job id
    id, err := a.Store.CreateTrainingJob(r.Context(), store.CreateTrainingJobParams{...})

    // ④ 审计：谁在何时提交了什么
    a.Store.Audit(r.Context(), operator, "operator", "training.submit", ...)

    // ⑤ 起一个后台 goroutine 去真正干活，请求立刻返回（不阻塞！）
    go a.runTrainingJob(trainingTarget{JobID: id, Operator: operator, Spec: ...})

    // ⑥ 立刻回 202 Accepted（"已受理，异步处理中"）
    WriteJSON(w, http.StatusAccepted, map[string]any{"id": id, "status": "pending"})
}
```
**机制讲清楚**：handler 只做"HTTP 层"的事——解析、校验、鉴权、调下层、组织响应。**它不自己写 SQL、不自己连 K8s**。真正的业务在 store 层和 runner 里。这就是"分层"的意义。
**`go a.runTrainingJob(...)` 是精髓**：训练可能跑几小时，不可能让 HTTP 请求干等。所以开一个 goroutine 异步干，请求 30 毫秒就返回 202。前端靠轮询看进度。

#### 第 4 站：store 层（数据访问——类型安全地落库）
真实代码 `server/internal/store/training.go`（精简）：
```go
func (s *Store) CreateTrainingJob(ctx, p CreateTrainingJobParams) (string, error) {
    hp, _ := json.Marshal(p.Hyperparams)      // 超参 map → JSONB
    var id string
    err := s.pool.QueryRow(ctx, `
        INSERT INTO training_jobs (name, framework, namespace, base_model, image,
                                   workers, gpus_per_worker, hyperparams, status, ...)
        VALUES ($1,$2,$3,$4,$5,$6,$7,$8::jsonb,'pending',...)
        RETURNING id`,
        p.Name, "pytorch", p.Namespace, p.BaseModel, p.Image, ...
    ).Scan(&id)                                // 把数据库返回的 id 读进 Go 变量
    return id, err
}
```
**机制讲清楚**：
- `s.pool` 是 **pgx 连接池**——复用数据库连接，不用每次新建（建连接很贵）。
- `$1,$2...` 是**参数化查询**——值和 SQL 分开传，数据库不会把值当 SQL 执行，**天然防 SQL 注入**。绝不字符串拼接 SQL。
- `RETURNING id` + `Scan(&id)`：插入并把自增/生成的主键读回来。
- 结构化字段（name/status）用表的列；灵活的东西（超参、进度事件）塞 **JSONB**（Postgres 能存 JSON 还能查）。

#### 第 5 站：响应回到前端
返回的 JSON 走统一信封；成功 `{"id":"...","status":"pending","registers_as":"..."}`，出错 `{"code":"...","message":"...","requestId":"..."}`。前端 `useMutation` 的 `onSuccess` 弹个 toast + 触发列表重拉，5 秒轮询接力显示 pending→running→succeeded/failed。**一次请求闭环完成。**

### B. Go 并发：后台任务怎么不阻塞请求（goroutine + runner）

真实代码 `server/internal/httpx/training_runner.go`（精简）——这是上面 `go a.runTrainingJob(...)` 起的后台流程：
```go
func (a *API) runTrainingJob(t trainingTarget) {
    ctx := context.Background()  // 脱离请求 context（请求早返回了，不能用它的 ctx）

    // 1. 向 K8s 提交 PyTorchJob（创建一个 Kubeflow 自定义资源）
    if _, err := a.Training.SubmitJob(ctx, t.Spec); err != nil {
        a.Store.UpdateTrainingJobStatus(ctx, t.JobID, "failed"); return
    }
    a.Store.UpdateTrainingJobStatus(ctx, t.JobID, "running")

    // 2. 每 5 秒轮询一次 K8s，问这个训练到哪一步了
    ticker := time.NewTicker(5 * time.Second)
    for range ticker.C {
        st, _ := a.Training.GetJob(ctx, t.Spec.Namespace, t.Spec.Name)
        a.trainingProgress(ctx, t.JobID, meta, st)  // 把相位/副本进度写回 DB 的 metadata
        switch st.Phase {
        case "Succeeded":
            a.finishTraining(...)         // 成功 → 自动注册进模型注册中心（C1 闭环）
            return
        case "Failed":
            a.finishTraining(...); return // 失败 → 回写 + 审计
        }
        if time.Now().After(deadline) { ...; return }  // 超时保护
    }
}
```
**机制讲清楚**：
- **goroutine** 是 Go 的轻量协程，`go f()` 就在后台并发跑 `f`，主流程（HTTP 请求）不等它。对比你熟的：像 Python 的 `asyncio.create_task` 或起个后台线程，但 goroutine 极轻（几 KB），开几万个无压力。
- 这个 runner 就是个**状态机轮询器**：提交 → running → 每 5 秒查 K8s → 改数据库状态 → 成功/失败/超时收尾。CI/CD 的滚动发布 runner（`deploy_runner.go`）是一模一样的形态。
- **为什么轮询而不是等回调？** K8s 是声明式的，你创建资源后它异步去调度，没有"训练完了打你电话"的机制，所以控制面主动轮询它的状态。

### C. K8s 写操作：client-go 真实代码

真实代码 `server/internal/k8s/client.go`——平台怎么"真的"改 K8s：
```go
// 扩缩容：改 Deployment 的副本数（弹性扩缩容能力的底层）
func (c *Collector) ScaleDeployment(ctx, namespace, name string, replicas int32) (int32, error) {
    scale, _ := c.clientset.AppsV1().Deployments(namespace).GetScale(ctx, name, ...)
    scale.Spec.Replicas = replicas                    // 改期望副本数
    updated, err := c.clientset.AppsV1().Deployments(namespace).UpdateScale(ctx, name, scale, ...)
    return updated.Spec.Replicas, err
}

// CI/CD：改 Deployment 镜像 = 触发滚动发布；返回旧镜像供回滚
func (c *Collector) PatchDeploymentImage(ctx, namespace, name, image string) (string, error) {
    dep, _ := c.clientset.AppsV1().Deployments(namespace).Get(ctx, name, ...)
    prev := dep.Spec.Template.Spec.Containers[0].Image   // 存旧镜像
    patch := fmt.Sprintf(`{"spec":{"template":{"spec":{"containers":[{"name":%q,"image":%q}]}}}}`, ...)
    c.clientset.AppsV1().Deployments(namespace).Patch(ctx, name, types.StrategicMergePatchType, []byte(patch), ...)
    return prev, nil   // 改完 K8s 会自动滚动替换 Pod；失败时用 prev 回滚
}
```
**机制讲清楚**：
- `c.clientset` 是 **client-go**（K8s 官方 Go 客户端）。`AppsV1().Deployments(ns).Get/Patch/UpdateScale` 直接调 K8s API Server 的 HTTP 接口。
- **声明式**：你不说"把 Pod 一个个杀了重建"，你只改 Deployment 的"期望镜像/期望副本数"，K8s 的控制器自己**调和**（reconcile）到你声明的状态——这就是滚动发布"自动"发生的原因。
- **怎么判断发布完成？**（面试常被追问）真实代码 `RolloutStatus` 对齐 `kubectl rollout status` 的逻辑：`观测代数 observedGeneration ≥ 期望代数` **且** `updated == ready == available == 期望副本数`，才算 complete；`Progressing` 条件变 `ProgressDeadlineExceeded` 就是 failed → 自动 patch 回旧镜像。

### D. 三个横切中间件的真实机制

- **限流（Redis 令牌桶）**：每个 IP 一个"桶"，按固定速率往桶里放令牌，每个请求拿一个令牌，桶空了就拒（HTTP 429）。用 Redis 是因为多个后端副本要**共享**同一个计数（分布式限流）。Redis 挂 → 放行（fail-open）。
- **幂等**：客户端给写请求带一个 `Idempotency-Key`。后端第一次处理后把结果存 Redis；同 key 再来直接返回上次结果，不重复执行。**解决"网络超时重试导致重复提交"**（比如重复触发同一次部署）。
- **认证授权**：
  - **Authn**：从 `Authorization: Bearer <token>` 解析 **JWT**——一个 `header.payload.signature` 的字符串，服务端用密钥（HS256）验签，验过就知道"你是谁"，放进请求 context。**无状态**：不用查 session 表。
  - **Authz**：看你的角色。`viewer < operator < admin`。读接口任意登录态可过，写接口（POST/PUT/PATCH/DELETE）需 operator 以上，否则 403。

### E. 数据库：migration → sqlc → 事务

- **migration（版本化建表）**：真实文件 `000012_training_jobs.up.sql` 就是一段 `CREATE TABLE training_jobs (...)`。程序启动时 golang-migrate 按编号顺序把没执行过的迁移跑一遍。**好处**：数据库结构进 Git、可重放、新环境一键建好 36 张表（E2E 实测：fresh DB 启动自动 "migrations applied"）。
- **sqlc（类型安全 SQL）**：你写 `.sql` 查询，sqlc 生成对应的 Go 函数 + 结构体。**编译期**就能发现"你 SELECT 的列和 Go 结构体字段对不上"。比手写拼 SQL/手写 Scan 安全得多。（训练表因为和 chat/knowledge 一样走"手写 pgx"而非 sqlc，是刻意选择——非核心表不进 sqlc 的 schema 列表。）
- **事务（ACID 的"原子性"实战）**：存储归档器 `storage_archiver.go` 的安全顺序——**先**把过期数据传 MinIO（成功），**再**在一个数据库事务里 `删 Postgres 行 + 写归档清单`。事务保证这两步"要么都成、要么都回滚"，绝不会出现"删了 PG 但清单没记"的脏状态。且只删**严格早于保留期**的行、对象层不可用就跳过——**绝不在没备份时删数据**。

### F. 前端：状态驱动渲染（和后端思维的最大区别）

你写 ML 是"过程式"：调函数、拿结果。前端 React 是"**声明式**"：你描述"UI 长什么样 = f(状态)"，**只改状态**，框架自动重渲染变化的部分。
- 提交训练 → `submit.mutate(input)` → 成功后 `invalidateQueries` → react-query 重拉列表 → `jobs.data` 变 → 表格组件自动重渲染出新行。**全程你没碰过一行"操作页面元素"的代码。**
- 组件 = UI 积木（按钮/表格/抽屉），各管自己的状态和渲染，可复用、可组合。页面只负责"把积木拼起来"。

## 5. 可以讲的"设计故事"（面试加分点）

挑 2-3 个讲深，比泛泛而谈强 10 倍：

1. **"从假数据到真执行"**：CI/CD 一开始是"记录状态机"（假装发布），后来升级成真的 `PatchDeploymentImage` + 轮询 `RolloutStatus` + 失败回滚旧镜像。讲清"怎么判断滚动发布完成"（observedGeneration 追平 + updated/ready/available 都等于期望副本数，对齐 `kubectl rollout status` 的逻辑）。

2. **"K8s 写操作的安全护栏"**：feature flag + 命名空间允许名单 + serving 命名空间硬禁三重保护，外加优雅降级。体现你对"在生产基础设施上做写操作有多危险"的敬畏。

3. **"分层存储生命周期"**：怎么安全地把热数据搬冷——先上传 MinIO 成功、再在事务里删 PG + 写归档清单、只删严格早于保留期的行、对象层不可用就跳过（绝不无备份删数据）。这是数据安全意识。

4. **"agentic 诊断"**：从单轮"塞证据给模型"升级到多轮"模型自己决定查什么工具"，无 GPU 时降级成确定性脚本但契约一致。这条直接接你的 LLM 强项。

5. **"训练→注册闭环"**：训练成功后自动注册模型版本、血缘指回基座、产物落 MinIO、回填任务记录。讲"成功路径需要真集群，无集群时在提交 PyTorchJob 这步优雅失败"——诚实边界。

6. **"全链路追踪串起 Go→Python→vLLM"**：靠 W3C traceparent 传播，一条 37-span 的跨服务瀑布。体现可观测工程能力。

## 6. 高频面试题 Q&A

### 系统设计 / 架构
- **Q：整体架构讲一下？** → 按 2.1 的图，从浏览器到 Go 控制面到各数据存储到 serving 栈，强调"单一后端入口 + 中间件链 + 分层 + 优雅降级"。
- **Q：为什么 Go 做控制面、Python 做 AI？** → Go 擅长高并发 I/O 密集的控制面 + 云原生生态（client-go）；Python 擅长 LLM 生态。各用所长，用 HTTP 解耦。
- **Q：怎么保证写操作安全？** → feature flag 默认关 + 命名空间守卫 + 审计 + 幂等 + 优雅降级。
- **Q：依赖挂了怎么办？** → fail-open 降级：缓存穿透、限流放行、对象层不可用跳过归档、AI 不可达返回 502 而非崩溃。混沌测试固化了这些路径。

### 后端
- **Q：goroutine 是什么？和线程区别？** → 用户态轻量协程，几 KB 栈，Go runtime 调度（M:N），开销远小于 OS 线程，可开几十万个。
- **Q：分层架构为什么这么分？** → handler 管 HTTP、store 管业务、数据访问独立——关注点分离、易测试、底层可替换。
- **Q：JWT 怎么工作？** → 登录后服务端签发一个签名的 token（header.payload.signature），客户端每次请求带在 Authorization 头，服务端用密钥验签，无状态（不查 session）。
- **Q：幂等怎么实现？** → 写请求带幂等键存 Redis，重复请求命中则返回上次结果。

### 数据库
- **Q：什么数据放 Postgres、什么放 Redis、什么放 MinIO？** → 见 3.3 一句话记忆。
- **Q：ACID 是什么？** → 原子性/一致性/隔离性/持久性，事务的四个保证。
- **Q：缓存一致性怎么保证？** → cache-aside + 写后失效（invalidate）；接受短暂不一致，靠 TTL 兜底。
- **Q：RAG 的向量检索怎么做的？** → 文档切块→embedding→存 pgvector→查询 embedding 做余弦相似度 top-k 检索。

### 云原生
- **Q：K8s 的 Deployment / HPA / 滚动更新讲一下？** → 见 3.4 核心概念。
- **Q：声明式是什么意思？** → 你声明期望状态，K8s 控制器持续调和现实到期望（reconciliation loop），而非命令式一步步操作。
- **Q：容器和虚拟机区别？** → 容器共享宿主内核、轻量、秒级启动；VM 带完整 OS、重、隔离更强。
- **Q：多阶段构建好处？** → 构建环境和运行环境分离，最终镜像只含二进制，小且安全。

### 前端
- **Q：React 核心思想？** → 声明式 UI = f(state)，状态驱动渲染，组件化复用。
- **Q：前后端怎么通信、怎么处理流式？** → REST/JSON + SSE（流式）；react-query 管缓存和轮询。
- **Q：TypeScript 解决什么？** → 静态类型，编译期抓错，类型即文档。

### AI / 你的主场
- **Q：vLLM 为什么快？** → PagedAttention（KV cache 分页管理）+ 连续批处理（continuous batching）。
- **Q：LoRA 是什么？** → 低秩适配，冻结基座只训练小的低秩增量矩阵，省显存、可热插拔多适配器。
- **Q：agentic 诊断和普通 RAG 区别？** → RAG 是一次检索一次生成；agent 是多轮，模型自己决定调哪些工具、看结果再决定下一步。
- **Q：分布式训练怎么编排的？** → Kubeflow Training Operator 把 PyTorchJob 拆成 master+worker 做 DDP，平台用 dynamic client 提交并轮询状态。

## 7. 作为"只懂 VLM 的人"，你该怎么讲

### 扬长
- **从 AI Infra 切入**：开场就讲"我做了一个管理真实 vLLM+LoRA 推理栈的平台"，把你的 LLM 知识当锚点，再往外扩到 K8s/后端/前端。面试官会觉得"这人懂 AI 又懂工程"。
- **重点讲你最熟的链路**：agentic 诊断（工具调用）、RAG（pgvector 检索 + 反馈回流）、训练闭环（Kubeflow + LoRA 注册）。这三块既是平台亮点又是你的主场。
- **强调"真执行"**：反复强调大多数能力是真调 K8s/真归档/真发布，不是假数据。这是和"教程级项目"的最大区别。

### 避短（被问到不熟的地方）
- 诚实 + 展示学习能力：*"前端我用 React+TS 搭了 16 个页面，遵循页面只组装、逻辑进 hook 的约定；更深的前端性能优化我还在学。"* ——承认边界比硬吹强。
- 把不熟的点拉回设计意图：被问 K8s 细节答不上时，回到"我做了三重安全护栏和优雅降级，因为在真集群上做写操作很危险"——展示工程判断力，而非死记 API。
- 主动标注诚实边界：*"这是作品集项目，没有真实用户流量；但 CI/CD、扩缩容、归档都是真执行的，训练成功路径需要真集群。"*

### 一定要能口述的 3 件事
1. 整体架构图（2.1）+ 一次请求的旅程（2.2）。
2. "什么数据放 PG/Redis/MinIO" + 为什么（3.3）。
3. K8s 写操作的安全护栏 + 优雅降级哲学（3.4 / 3.7）。
