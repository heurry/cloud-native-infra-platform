# UI 页面设计准则

本文档用于固化后续页面设计的基本方法，避免页面退化为“数据和功能的堆叠页”。适用于 AI Infra Dashboard、服务治理页、可观测性页面、知识库 / RAG 页面、模型管理页、压测页、Copilot 问答页等。

## 核心原则

页面设计不能从“有哪些接口、有哪些字段、有哪些组件”开始，而要从“用户进入这个页面要完成什么判断或动作”开始。

差的页面通常是：

```text
接口有什么数据
字段全部拿出来
卡片 / 表格 / 图表平铺
用户自己寻找重点
```

好的页面应该是：

```text
用户是谁
他先要判断什么
哪些信息最重要
哪些信息只是诊断明细
按任务路径逐层展开
```

一句话原则：

```text
不要做数据陈列页，要做辅助用户决策的产品界面。
```

## 设计前必须回答的问题

每个页面开始设计前，先写出下面这份页面设计契约。

```text
页面目标：
用户进入这个页面，最想知道什么？

用户角色：
研发 / 运维 / SRE / 平台运营 / 管理者

首屏必须回答：
1. 当前状态是什么？
2. 是否有异常或重点？
3. 用户下一步可以做什么？

信息层级：
一级信息：必须首屏出现，用于判断状态
二级信息：用于解释原因和趋势
三级信息：用于诊断、追踪、审计、详情

布局结构：
Header
核心概览
主内容
辅助诊断
明细数据

交互策略：
哪些默认展示？
哪些放入 Tab？
哪些折叠？
哪些内部滚动？
哪些需要固定在页面底部或侧边？

视觉约束：
主色、告警色、卡片半径、表格密度、图表高度、栅格列数
```

如果这些问题没有答案，不应直接开始写 UI。

## 信息架构优先级

页面信息应该按用户认知路径组织，而不是按后端数据结构组织。

通用顺序：

```text
1. 当前上下文
2. 当前状态
3. 核心指标
4. 趋势和异常
5. 原因和瓶颈
6. 明细数据
7. 操作入口
```

例如指标监控页应该回答：

```text
系统现在健康吗？
性能有没有异常？
瓶颈在哪里？
需要查看哪些明细？
```

因此结构应该是：

```text
顶部：监控上下文 + 健康状态 + 时间范围
第一层：核心 KPI
第二层：性能趋势与异常诊断
第三层：资源状态和瓶颈定位
第四层：请求日志、Pod、容器等明细
```

而不是：

```text
KPI
图表
GPU 表格
Pod 表格
Host 表格
cAdvisor 表格
请求日志
全部平铺
```

## 首屏规则

首屏只服务于判断，不服务于穷尽。

首屏应该尽量回答：

```text
我在哪个页面？
当前对象是什么？
当前时间范围是什么？
整体状态是否正常？
最关键的 3-5 个指标是什么？
是否有异常？
```

首屏不应该出现：

```text
大量长表格
过多同质 KPI
没有主次的图表
无业务语义的卡片
需要用户滚动后才知道页面目标
```

## KPI 设计规则

KPI 不是越多越好。一个页面首屏建议最多保留 4-6 个核心 KPI。

每个 KPI 卡片应包含：

```text
业务名称
主指标
次指标
单位
趋势或状态
```

错误示例：

```text
QPS
请求数
错误数
错误率
P50
P95
P99
TTFT
输入 Tokens
输出 Tokens
全部一排小卡片
```

更好的示例：

```text
吞吐：QPS + Tokens/s
延迟：平均 TTFT + P95 TTFT
端到端延迟：P95 + P99
稳定性：错误率 + 请求数
Token 用量：输入 + 输出
```

## 图表设计规则

图表必须服务于判断，不是为了让页面看起来“有数据”。

每个图表应该明确回答一个问题：

```text
吞吐有没有变化？
延迟是否异常？
错误是否增加？
资源是否饱和？
请求是否集中到某个目标？
```

图表设计约束：

```text
一个图表只表达一个主要主题
主图可以大，辅助图可以小
图表高度稳定
颜色有语义
图例清晰
不要把所有曲线塞进一个图
```

## 表格设计规则

表格通常是诊断明细，不应该默认成为页面主视觉，除非页面目标就是数据检索。

表格应分为两类：

```text
概览表：只保留关键字段
明细表：默认折叠、放入 Tab 或内部滚动
```

当出现多个长表格时，必须使用：

```text
Tab
折叠面板
内部滚动
详情按钮
筛选条件
```

不要把多个表格连续平铺在页面上。

## 渐进披露规则

页面应该按信息重要性逐层展开。

推荐结构：

```text
一屏看状态
二屏看瓶颈
三屏看明细
```

常用方式：

```text
Tab：同类资源切换，如 GPU / Pod / 主机 / 容器
折叠：低频诊断项
内部滚动：请求日志、容器列表、长表格
详情按钮：跳转到单条记录或单个资源
```

## 业务语义规则

页面必须体现当前业务场景，不要只是通用后台模板。

例如 AI Infra 指标页应该出现：

```text
Healthy / Warning
QPS
TTFT
P95 / P99
Tokens/s
GPU 利用率
KV Cache
Pod 路由分布
请求追踪
兜底原因
诊断建议
```

服务治理页应该出现：

```text
服务实例列表
运行时健康
Gateway / vLLM 路由状态
心跳 / TTL
最近事件
快速健康探测
```

知识库 / RAG 页应该出现：

```text
语料来源（基准测试日志）
文档列表
向量索引状态
检索召回预览
重建索引
检索增强问答入口
```

业务页面没有业务语义，就会显得像临时后台。

## 视觉系统规则

同一套产品内应保持一致的视觉约束。

推荐基础规范：

```text
背景：#F6F8FA
卡片：#FFFFFF
主文字：#0F172A
次文字：#64748B
边框：#E5E7EB
主色：#0F766E / #047857
信息：#2563EB
警告：#D97706
错误：#DC2626
```

组件约束：

```text
卡片圆角：8px - 12px
卡片边框：1px solid #E5E7EB
阴影：轻量，不要厚重
页面间距：统一栅格
按钮：明确主次
表格：行高稳定，内容过长省略
图表：高度固定，避免挤压布局
```

不要在同一页面混用多套圆角、阴影、颜色和间距。

## 页面模板

### 1. 可观测性 Dashboard

适用于指标、监控、压测结果、系统状态。

```text
Header：标题 + 范围 + 刷新 + 健康状态
KPI：4-6 个核心指标
主图：吞吐 / 延迟 / 错误趋势
诊断：路由 / GPU / 兜底 / 异常
资源：Tab 切换
明细：请求日志 / Pod / 容器表格
建议：自动诊断或人工排查建议
```

### 2. 运营工作台

适用于配置发布、事件处置、服务治理等平台运营场景。

```text
Header：当前工作台和关键动作
KPI：待处理数量、今日新增、风险项
主区域：当前重点对象
侧栏：列表、筛选、快速操作
底部：策略、流程、明细记录
```

### 3. Copilot / 问答助手页

适用于检索增强问答、诊断对话等交互场景。

```text
Header：会话标题和模型 / 端点选择
左侧：会话列表
中间：对话流（含检索引用和路由信息）
右侧：证据 / 推荐操作
底部：输入框和发送状态
```

### 4. 知识库 / 配置管理

适用于文档、模型、配置、数据源管理。

```text
Header：对象类型 + 创建/导入操作
左侧：分类、筛选、集合
中间：列表或详情
右侧：元信息、版本、操作
底部：日志、引用、关联资源
```

## 设计检查清单

实现前检查：

```text
[ ] 页面目标是否明确？
[ ] 用户角色是否明确？
[ ] 首屏是否能回答当前状态？
[ ] 是否只保留了最关键 KPI？
[ ] 图表是否有明确判断价值？
[ ] 长表格是否被 Tab / 折叠 / 滚动管理？
[ ] 是否体现了业务语义？
[ ] 是否有明确主次操作？
[ ] 是否避免了所有数据平铺？
[ ] 是否复用了现有设计系统？
```

实现后检查：

```text
[ ] 1366px 宽度下没有横向错位
[ ] 1920px 宽度下内容不过度拉散
[ ] 表格内容不会撑破卡片
[ ] 长内容有滚动或省略
[ ] 按钮文字不溢出
[ ] 图表高度稳定
[ ] 页面首屏重点清楚
[ ] 用户不需要读完所有内容才知道页面用途
```

## 给 Codex / 开发者的执行约束

后续实现页面时，默认遵守以下顺序：

```text
1. 先定义用户任务和页面目标
2. 再定义信息层级
3. 再选页面模板
4. 再布局
5. 最后接数据和补细节
```

不要直接从接口字段生成 UI。

当用户没有提供设计图时，应主动选择最贴近业务类型的成熟产品范式：

```text
监控页：Datadog / Grafana Cloud / New Relic 风格
AI 调试页：LangSmith / OpenAI Platform 风格
运营后台：Linear / Retool / Modern SaaS Console 风格
知识库 / Copilot：Notion AI / Perplexity 风格
```

如果页面看起来像“数据平铺页”，应立即重构为：

```text
概览
趋势
诊断
明细
操作
```

这是后续所有复杂页面的默认信息架构。
