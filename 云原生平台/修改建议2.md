这张生成图和你之前的版本相比，最大的变化不是“多画了几个图表”，而是它把页面从**信息堆叠型后台**升级成了**任务驱动型运维控制台**。

可以总结成一句话：

> 之前的页面是在“展示 Kubernetes 信息”，现在这版是在“引导用户完成一次 AI 运维诊断与修复”。

## 一、和之前版本的核心差别

### 1. 页面主线更明确：从资源面板变成运维流程

你之前的页面虽然也有流程条，但整体还是偏“资源总览 + 表格 + 事件列表”。

新图里最上方的流程条被强化成了页面主线：

```text
发现问题 → 定位对象 → 分析原因 → 推荐动作 → 执行修复 → 验证恢复
```

而且当前步骤“分析原因”被高亮，左右步骤有明确的完成 / 待执行状态。

这让用户进入页面后，第一眼就知道：

```text
现在发生了什么？
诊断进行到哪一步？
下一步应该做什么？
```

这比单纯展示 Pod、Node、Workload 数量更高级。

---

### 2. 信息层级更清晰

之前页面的结构大致是：

```text
指标卡片
集群概览
Workload 表格
事件列表
GPU 调度
弹性伸缩
右侧 AI Copilot
```

所有模块都比较“平级”，用户需要自己判断重要性。

新图的层级更清楚：

```text
第一层：运维流程条，告诉用户当前处于什么阶段
第二层：核心指标卡片，快速判断集群状态
第三层：集群资源概览，定位基础设施环境
第四层：Workload 表格，定位具体异常对象
第五层：诊断详情，提供证据链和趋势图
右侧：AI Copilot，给出判断和动作
```

也就是说，新版不是把信息全部铺出来，而是按照用户决策路径组织信息。

---

### 3. 核心指标卡片更有“状态感”

之前的指标卡片主要是：

```text
Pod 10
工作负载 128
节点 16
告警事件 3
GPU 分配 3/4
```

信息是对的，但视觉上比较静态。

新图加入了小型趋势图和环形占比图：

```text
Pod：数字 + 小折线趋势
Workload：数字 + 小折线趋势
GPU 分配：3/4 + 75% 环形图
```

这样做的好处是：

```text
数字告诉你当前值
趋势告诉你是否恶化
占比告诉你资源余量
```

例如 GPU 3/4 单看数字还不够直观，但配上 75% 环形图后，用户马上能理解资源接近紧张状态。

---

### 4. 集群概览从“大卡片”变成“对象摘要”

之前的集群概览已经有卡片，但视觉上和上面的指标卡片差别不大。

新图里集群概览变成了更规整的资源对象摘要：

```text
集群：minikube-gpu
命名空间：default
节点池：gpu-pool-a
容器运行时：containerd
Kubernetes 版本：v1.30
Ingress：Envoy Gateway
Service Mesh：Istio sidecar
Storage：local-path / model-pvc
CPU 节点：2
Autoscaler：HPA + KEDA
```

这些内容不是主要告警，所以视觉权重低于核心指标，但又比普通说明更结构化。

这类设计很适合云原生平台，因为用户经常需要快速确认当前操作环境。

---

### 5. Workload 表格更像企业级控制台

新版表格相比之前更成熟，主要体现在几个地方：

```text
增加了筛选器
增加了搜索框
增加了类型 / 状态筛选
增加了状态标签
增加了风险标签
增加了操作入口
增加了分页
```

之前的表格更像“数据展示”，新版更像“可操作资源列表”。

企业级云平台的表格通常都需要这些能力：

```text
搜索
筛选
排序
状态标签
批量操作
单行操作
详情抽屉
分页
```

所以这一版更接近真实产品。

---

### 6. 诊断详情不再只是事件列表，而是证据看板

之前下方主要是 Tabs + 事件内容。

新版下方仍然保留 Tabs，但内部内容丰富了很多：

```text
左侧：Events 列表
中间：GPU 调度状态图
右侧：节点资源压力进度条
右侧：SLO 影响分析
```

这个改动非常关键。

因为 AI Ops 页面不能只展示“事件”，还应该展示：

```text
事件发生了什么
资源状态如何变化
是否影响业务 SLO
哪个对象最可能是根因
```

图表的加入让证据链更完整。

---

### 7. 右侧 AI Copilot 更像“决策面板”

之前的 Copilot 更多是：

```text
当前问题
影响对象
推荐动作按钮
输入框
```

新版右侧更完整：

```text
当前告警摘要
影响范围
异常对象标签
推荐动作列表
优先级
风险等级
预计恢复时间
生成变更计划
查看建议
诊断深度选择
对话输入框
```

这就从“聊天助手”变成了“运维决策面板”。

尤其是推荐动作卡片：

```text
1 扩容 GPU 节点
2 调整 HPA 参数
3 回收空闲 GPU 资源
```

每个动作都有上下文，用户知道为什么做、风险多大、预期多久恢复。

# 通用页面改造逻辑

## 1. 所有页面先定义“用户任务链路”

不要先想页面放什么模块，而要先想用户在这个页面要完成什么任务。

例如 Kubernetes 页：

```text
发现异常 → 定位 Workload → 查看资源状态 → 分析调度原因 → 执行扩容 / 调整 HPA
```

AI Ops 页：

```text
发现 Incident → 聚合证据 → 判断根因 → 生成修复计划 → 审批执行 → 验证恢复
```

模型服务页：

```text
查看模型状态 → 定位延迟 / 吞吐问题 → 查看实例和 GPU → 调整副本 / 灰度发布
```

配置中心页：

```text
查看配置版本 → 对比变更 → 评估影响 → 发布 / 回滚 → 审计记录
```

页面布局要围绕这个链路展开。

---

## 2. 每个页面统一使用“五层结构”

建议平台所有页面都套用这个结构：

```text
第 1 层：任务流程 / 当前状态
第 2 层：核心指标
第 3 层：资源对象 / 主表格
第 4 层：诊断证据 / 图表 / Tabs
第 5 层：AI Copilot / 推荐动作
```

对应到页面：

```text
顶部流程条：告诉用户当前处于哪一步
指标卡片：告诉用户整体健康状况
资源表格：告诉用户哪个对象异常
诊断区域：告诉用户为什么异常
AI Copilot：告诉用户下一步怎么做
```

这套结构可以直接复制到其他模块。

---

## 3. 卡片要分三类，不要所有卡片一个样

### A. 指标卡片

用于展示关键数值。

适合内容：

```text
Pod 数
Workload 数
节点数
告警数
GPU 利用率
P95 延迟
QPS
错误率
成本
```

推荐样式：

```text
标题
大数字
状态说明
小趋势图 / 环形图 / 同比变化
```

例如：

```text
GPU 分配
3 / 4
75% 插槽利用率
环形图
```

---

### B. 对象卡片

用于展示资源对象。

适合内容：

```text
集群
命名空间
节点池
网关
Service Mesh
存储卷
运行时
Kubernetes 版本
```

推荐样式：

```text
图标
对象类型
对象名称
辅助说明
```

对象卡片不要抢指标卡片的视觉权重。

---

### C. 动作卡片

用于展示 AI 推荐操作。

适合内容：

```text
扩容 GPU 节点
调整 HPA
回滚配置
重启实例
执行 Benchmark Replay
生成变更计划
```

推荐样式：

```text

动作标题
原因说明
风险等级
预计耗时
主操作按钮
```

## 4. 图表使用原则

你看到的新图里加了折线图、环形图、柱状图、进度条，这个方向是对的，但图表不能乱加。

建议这样使用：

| 图表类型         | 使用场景                         |
| ------------ | ---------------------------- |
| 小折线图         | 指标趋势，例如 Pod、QPS、P95、错误率      |
| 环形图          | 资源占比，例如 GPU 分配、CPU 使用率、存储使用率 |
| 柱状图          | 调度分布、请求量、错误分布、实例负载           |
| 横向进度条        | 节点压力、资源水位、SLO 消耗             |
| Timeline     | Incident 过程、发布流程、RCA 推理链     |
| Sankey / 拓扑图 | 服务调用链、流量路径、依赖关系              |

具体规则：

```text
能表达趋势，用折线图
能表达占比，用环形图
能表达分布，用柱状图
能表达压力，用进度条
能表达过程，用时间线
能表达依赖，用拓扑图
```

不要为了好看而加图表，每个图表都要服务判断。

---

## 5. 表格要从“数据列表”升级成“资源控制台”

所有资源类页面的表格都建议统一为：

```text
标题栏：表格名称 + 当前范围
工具栏：搜索 + 筛选 + 刷新 + 自定义列
表头：支持排序
单元格：状态标签 / 风险标签
行操作：查看详情 / 日志 / AI 诊断 / 更多
底部：分页
```

例如模型服务页表格：

```text

```

```text

```

发布流水线页表格：

```text
流水线 | 分支 | 镜像版本 | 阶段 | 通过率 | 最近运行 | 状态 | 操作
```

## 7. 右侧 AI Copilot 统一成“摘要 + 动作 + 对话”

右侧 Copilot 不要每页重新设计，建议统一结构：

```text
AI Copilot
├── 当前问题摘要
├── 影响范围
├── 关键证据
├── 推荐动作
├── 风险等级
├── 执行入口
├── 诊断模式
└── 对话输入
```

不同页面只替换内容，不替换结构。

比如：

### Kubernetes

```text
当前问题：GPU 调度压力
影响范围：qwen3-4b-platform
推荐动作：扩容节点 / 调整 HPA / 回收空闲 GPU
```

### 模型服务

```text
当前问题：TTFT 升高
影响范围：qwen3-4b-platform
推荐动作：增加 vLLM 副本 / 调整 batch size / 检查 KV cache
```

### 配置中心

```text
当前问题：redis config v8 引发延迟
影响范围：redis-cache、qwen3-4b-platform
推荐动作：回滚 v7 / 灰度验证 / Benchmark replay
```

这样整个产品会非常统一。

## 8. 弹窗、抽屉、折叠的统一规则

这点非常重要。

```text
页面主体：展示主流程
Tabs：收纳诊断证据
抽屉：查看对象详情
弹窗：确认高风险操作
折叠：隐藏低频信息
```

具体规则：

| 交互   | 用途                        |
| ---- | ------------------------- |
| 右侧抽屉 | Workload 详情、Pod 详情、模型实例详情 |
| 底部抽屉 | 日志、Trace、YAML、执行输出        |
| 折叠面板 | Tool Calls、历史事件、审计记录      |
| 弹窗   | 扩容、回滚、重启、删除、生产变更确认        |
| 全屏页  | 复杂拓扑、大规模日志分析、完整 RCA 报告    |

不要用弹窗放大段信息，也不要把所有详情都堆在主页面。

## 四、可以直接套用的页面设计公式

你可以把所有页面都按这个公式改：

```text
页面 = 左侧导航 + 顶部环境栏 + 主任务流程 + 核心指标卡片 + 资源对象区 + 主表格 + 诊断 Tabs + 右侧 AI Copilot
```

更具体一点：

```text
1. 先放流程条，告诉用户当前任务阶段。
2. 再放 4–5 个核心指标，最好带趋势或占比。
3. 再放资源对象卡片，说明当前操作环境。
4. 中间放主对象表格，支持搜索、筛选、状态、风险、操作。
5. 下方放诊断详情，用 Tabs 收纳证据。
6. 右侧固定 AI Copilot，展示问题、影响范围和推荐动作。
7. 高风险动作统一进入确认弹窗。
```

## 六、最终统一设计原则

可以沉淀成这套原则：

```text
1. 页面不按功能堆模块，而按运维任务链路组织。
2. 顶部用流程条表达当前阶段，强化 AI 运维闭环。
3. 核心指标必须图形化，至少包含趋势、占比或变化方向。
4. 资源对象用低权重卡片展示，避免抢占主指标视觉。
5. 主对象统一用企业级表格，必须支持搜索、筛选、状态、风险和操作。
6. 诊断证据统一放入 Tabs，避免平铺造成信息噪声。
7. AI Copilot 固定在右侧，统一为摘要、影响、证据、动作、对话五段式。
8. 推荐动作必须带优先级、风险等级、预计耗时和审批状态。
9. 图表只服务判断，不做装饰。
10. 详情用抽屉，高风险动作用弹窗，历史和原始信息用折叠。
```

---

## 七、你后续做页面时的检查清单

每做一个页面，都可以检查下面这些问题：

```text
用户进入页面后，能否 3 秒内知道当前最大风险？
是否有一个明确的运维流程条？
核心指标是否带趋势或占比？
是否有主对象表格？
异常对象是否能被一眼识别？
诊断信息是否被 Tabs 收纳？
右侧 AI Copilot 是否给出下一步动作？
推荐动作是否说明风险和预计影响？
点击详情是否进入抽屉，而不是堆在页面里？
执行生产操作前是否有确认弹窗？
```

如果都满足，这个页面就会比较成熟。
