# 11 Go 后端迁移计划（Java → Go 主后端）

> 决策（2026-05-30）：将平台后端从 **Java/Spring Boot 主后端** 迁移为 **Go 主后端**。
> 打法：**strangler-fig（绞杀者）+ 契约优先 + 双跑对拍**，全程前端可用，不做大爆炸式重写。
> 配套：`02-system-architecture.md`（架构）、`09-后端开发计划.md`（原 Java 计划，本文取代其后端语言路线）、`10-任务清单.md`（前端任务）。
> 勾选规则：`[ ]` 待办 / `[~]` 进行中 / `[x]` 完成。

---

## 1. 背景与目标

当前真实链路：

```text
React → Java/Spring Boot(:8080, PostgreSQL) → Go Agent(client-go) → Kubernetes
```

问题：真正读 k8s 的是 Go Agent，Java 只是在前面再包一层经 `AgentClient` 转发；后端语言重心偏离了"云原生/Infra/Go"的项目定位。

目标态：

```text
React 控制台
   │ REST / SSE
   ▼
┌─────────────────────────────┐
│  Go 控制面 API   ← 主后端     │
│  chi + pgx + client-go        │
│  配置中心 / 部署 / 事件 /      │
│  审计 / 元数据·总览 / 可观测聚合 │
└───┬───────────────┬─────────┘
    │               │
    ▼               ▼
 PostgreSQL     Kubernetes (client-go)
                    ▲
 Go Node Agent (DaemonSet) ── host / gpu / k8s 采集
    │
    ▼  (AIOps 调用)
 Python AI 服务 (FastAPI)
  RAG / 诊断 / chat（训练·评测为离线脚本）

  Java backend: 退役 ✗
```

核心收益：对接 k8s 的代码与对外 API 统一在 Go 生态；`React→Java→Agent→k8s` 收敛为 `React→Go→k8s`，少一跳、更贴 k8s 控制面惯用写法。

---

## 2. 迁移原则

1. **契约优先**：前端 `apps/web/src/types/ops.ts` + 现有 Java Controller 的请求/响应 JSON 即为 Go 必须复刻的契约（详见 §6）。
2. **绞杀者模式**：Go 后端在新端口 `:8081` 立起，与 Java `:8080` 并存；按"接口组"逐组把前端代理切到 Go；全切完再删 Java。
3. **双跑对拍**：同一份 PostgreSQL 数据下，逐接口对比 Go 输出 vs Java 输出（JSON diff），一致后才切。
4. **不动的东西**：PostgreSQL、前端代码、`agent/`、docker-compose 的 postgres/go-agent 服务——前端只切代理目标 `VITE_PROXY_TARGET`。

## 3. 技术选型（默认值，待 §4 拍板）

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 语言/版本 | Go 1.22（与 `agent/go.mod` 对齐） | 复用 agent 工具链 |
| 路由 | **chi** | 贴近 stdlib、中间件干净（Gin 备选） |
| DB 访问 | **pgx + sqlc** | SQL-first、类型安全，直接复用现有 PG schema（gorm 备选） |
| 迁移 | **golang-migrate** | `V1–V3.sql` 是 PG→PG，几乎原样搬 |
| 日志 | slog（结构化） | 标准库 |
| 配置 | env（`SPRING_DATASOURCE_*` 同名复用） | 与 compose 对齐 |
| 工程 | `go.work` 将 `agent/` + 新 `server/` 纳入同一 workspace | 双二进制、依赖统一 |

PostgreSQL、docker-compose、前端均不变。

## 7. 风险与注意

1. **百分位算法保真**：`/api/metrics/current` 的 p50/p95/p99 计算口径必须与 Java `MetricsService` 一致，否则 Observability/Overview 数值漂移。建议先抽出算法、用同一批 `request_traces` 单测对拍。
2. **错误信封一致**：前端已按 Java 的 `ApiError` 形态做了 `describeError`；Go 错误 JSON 结构（字段名、状态码）需对齐，否则前端报错处理失效。
3. **审计写入时机**：Java 在写操作 best-effort 落审计；Go 要么用中间件统一拦截写操作，要么各 handler 显式调用——选定其一，避免漏审计。
4. **迁移期双后端**：P0–P3 期间 Java 与 Go 并存属预期；务必逐组对拍后再切代理，避免"切了没对拍"导致前端字段缺失。
5. **schema 单一真相**：迁移期 Go(golang-migrate) 与 Java(Flyway) 都可能动 schema——迁移期间冻结 Flyway，schema 变更只走 golang-migrate，防止双写冲突。
