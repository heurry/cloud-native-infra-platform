## 1. 平台定位判断

当前项目应继续定位为：

> 面向云原生微服务与 AI 模型服务的统一基础设施控制平面，围绕服务治理、配置管理、Kubernetes 资源观测、可观测性、发布门禁、分层存储、元数据治理与 AI Ops 诊断闭环组织产品体验。

前端不应走普通 CRUD 后台或单纯监控大屏路线。当前页面已经具备平台雏形：左侧导航、顶部环境栏、右侧 AI Copilot、KPI、资源表格、闭环流程条、配置/部署交互都已经存在。下一阶段重点不是继续堆页面，而是把已有页面改成一个能讲清楚“资源状态 -> 指标证据 -> 风险判断 -> 建议动作 -> 验证结果”的生产工作台。

## 3. 后端实现现状对前端的影响

### 3.1 已可对接的能力

当前 Java 后端已经能支撑这些前端页面继续深化：

| 后端能力 | 接口 | 前端页面 | 建议 |
| --- | --- | --- | --- |
| 平台健康 | `GET /api/health` | 顶栏 / Settings | 顶栏增加后端健康与 Agent 健康状态 |
| 平台概览 | `GET /api/platform/overview` | Dashboard | 首页应消费 services、active_alerts、k8s available/error |
| 服务实例 | `GET /api/service-instances` | Model Serving / Models | 增加路由、SLO、版本、runtime binding 视图 |
| 健康检查 | `POST /api/service-instances/{name}/healthcheck` | Model Serving / Models | 行内 healthcheck 已有，可补最近检查结果与审计 |
| Kubernetes 快照 | `GET /api/kubernetes/{pods,deployments,snapshot}` | Kubernetes / Dashboard | 已有真实契约；前端需强化 unavailable 状态和详情抽屉 |
| 指标当前值 | `GET /api/metrics/current` | Observability / Dashboard / Services | host 已接入，GPU/cadvisor 需明确 unavailable/empty |
| 指标历史 | `GET /api/metrics/history` | Observability | 趋势图已可用，建议统一时间窗组件 |
| 请求追踪 | `GET /api/metrics/requests` | Observability / AI Ops | 异常 trace 跳 AI Ops 已有，但 AI Ops 尚未读取 query 上下文 |
| 配置中心 | `GET/POST /api/config/items`、versions、rollback | Config | 后端已可写，前端需加 Diff、影响范围、确认弹窗 |
| 审计事件 | `GET /api/audit/events` | Config / Settings / AI Ops | 建议做全局审计流与证据引用 |
| 部署记录 | `GET/POST /api/deployments`、finish、rollback | Pipelines | 前端需把部署和 gate、benchmark、config/model version 串起来 |
| Incident | `GET/POST /api/incidents`、ack、resolve | AI Ops / Dashboard | AI Ops 主页面目前仍是静态 incident，应改接真实接口 |

### 3.2 目前前后端不匹配的能力

| 前端已出现的能力 | 当前问题 | 建议 |
| --- | --- | --- |
| Knowledge / RAG | 前端请求 `/api/knowledge/documents`，当前 Java 后端返回 404 | 要么把 FastAPI RAG 能力代理到 Java，要么在 Java 新增 KnowledgeController |
| Benchmarks | 页面能启动 `/api/benchmarks/serving`，Java 后端当前没有对应 Controller | Benchmark worker 可以仍由 Python 执行，但 Java 应暴露统一控制面接口 |
| AI Ops Copilot | 右侧面板请求 `/api/aiops/benchmarks`、sessions、SSE stream，当前 Java 后端缺口明显 | 先做只读 diagnose/report 接口，再接流式会话 |

| Kubernetes Node/GPU 调度 | 接口有 snapshot，但当前环境 minikube 不可达；节点、HPA、GPU 调度仍多为静态 | 前端要清晰区分“数据不可用”和“系统健康” |

## 4. 总体前端修改建议

### 4.1 导航：主导航按平台能力域组织，闭环阶段留在页面内

当前左侧导航按 `01 发现问题 -> 06 验证恢复` 分组，演示叙事强，但长期使用会有两个问题：

- `AI Ops` 和“诊断建议”重复出现，容易造成入口混淆。
- 用户找配置、部署、模型、Kubernetes 时需要先理解闭环阶段。

建议主导航改为能力域：

```text
平台总览
模型服务
Kubernetes
可观测性
AI Ops
知识库 / RAG
配置中心
发布流水线
压测验证
模型注册
Demo 应用
平台设置
```

页面内继续保留闭环流程条，用于表达当前页面在故障处理链路中的位置。这样既保留演示叙事，又让导航更像真实控制台。

涉及文件：

- `apps/web/src/components/layout/AppSidebar.tsx`
- `apps/web/src/types/navigation.ts`

### 4.2 三栏布局：1180px 下应主动折叠 Copilot

普通页面在 1180px 截图中已经隐藏右侧 Copilot，主区可读性较好；但 AI Ops 页面仍保留右侧 `AIOpsCopilotPanel`，导致主工作区被压窄，Incident 表格和筛选区拥挤。

建议：

- `<=1280px` 时 AI Ops Copilot 默认折叠成右侧 48px 浮条。
- `<=1180px` 时 Copilot 改为 drawer，不占用 grid column。
- 三栏布局使用 CSS 变量控制：`--sidebar-width`、`--copilot-width`、`--topbar-height`。

涉及文件：

- `apps/web/src/styles.css`
- `apps/web/src/components/layout/AIOpsCopilotPanel.tsx`
- `apps/web/src/components/layout/AICopilotPanel.tsx`

### 4.3 数据状态：不要把“无数据”渲染成健康

当前部分 KPI 在接口返回空数组或 null 时仍显示绿色，例如模型服务中的 `副本健康 2/2` 但服务实例状态实际为 `unknown`。这会误导用户。

建议状态分级：

```text
success：真实健康、明确通过
warning：降级、不可达、等待确认
danger：失败、SLO 阻塞
neutral：未知、无数据、未配置
info：只读信息、人工模式
```

规则：

- `unknown` 必须是 neutral，不要当作 success。
- `available=false` 显示 warning，并显示具体原因。
- 指标缺失显示 `—`，并加 `数据源未接入`，不要显示 `0`。
- 静态示例数据必须有 `Demo` 或 `Placeholder` 标识。

涉及文件：

- `apps/web/src/components/common/PlatformPrimitives.tsx`
- `apps/web/src/pages/ServicesPage.tsx`
- `apps/web/src/pages/ModelsPage.tsx`
- `apps/web/src/pages/PlatformOverviewPage.tsx`

### 4.4 表格：修复列数不匹配，沉淀真正的 DataTable

截图中配置中心和发布流水线表格有明显问题：`操作` 表头和行内按钮被挤到下一行。原因是页面传了 9 列，但 CSS grid 只定义了 8 列。

当前问题：

- `.config-table.rich` 定义 8 列，`ConfigCenterPage` 渲染 9 列。
- `.pipeline-table.rich` 定义 8 列，`PipelinesPage` 渲染 9 列。
- 部分 `infra-action-btn` 背景使用 `var(--accent)`，但 `--accent` 是 HSL 分量，不是 CSS color，导致按钮背景失效、白字几乎不可见。

建议立即修：

- `.config-table.rich` 和 `.pipeline-table.rich` 补齐操作列。
- `.infra-action-btn` 使用 `background: hsl(var(--primary));` 或直接使用语义色变量。
- `DataTable` 支持 `columns` 配置携带 width，而不是每个页面单独写 CSS。
- 表格默认支持内部横向滚动，不撑破主布局。

涉及文件：

- `apps/web/src/components/common/PlatformPrimitives.tsx`
- `apps/web/src/styles.css`
- `apps/web/src/pages/ConfigCenterPage.tsx`
- `apps/web/src/pages/PipelinesPage.tsx`

### 4.5 Copilot：从“提示面板”升级为“上下文决策面板”

普通 Copilot 已经按页面变化，这是对的。下一步要做的是让 Copilot 与真实页面数据联动。

建议统一五段式：

```text
当前问题
影响对象
关键证据
推荐动作
问答输入
```

具体要求：

- Dashboard Copilot 使用 `/api/platform/overview`、active_alerts、k8s error。
- Kubernetes Copilot 使用 snapshot 的 `available/error/events`。
- Observability Copilot 使用 `metrics/current` 的 P95、error rate、trace count。
- Config Copilot 使用最近审计和配置版本变更。
- Pipelines Copilot 使用 running/failed deployment 和 gate 状态。
- AI Ops Copilot 不应只依赖 benchmark，会话入口要能处理 Incident、trace、workload、config 四类上下文。

## 5. 分页面修改建议

### 5.1 平台总览 Dashboard

当前问题：

- 首屏能看到 KPI 和快速跳转，但平台能力表达还偏弱。
- 缺少清晰的服务拓扑、AI Serving Runtime、发布门禁、存储与元数据概览。
- `active_alerts=1` 时首页仍以“平台运行正常”为主，风险优先级不够高。

建议改为四区：

1. `Platform Health`：健康分、服务实例、活跃模型、K8s 状态、GPU 健康、打开 Incident、部署成功率。
2. `Service & Model Topology`：API Gateway、Service Mesh、业务服务、AIBrix Gateway、Router、vLLM Replicas、Redis、Vector Store、Config Center、Observability Stack。
3. `AI Serving Runtime`：TTFT、P95、tokens/s、queue length、KV cache、GPU util、router strategy。
4. `Ops Loop`：Alert、Evidence、Diagnosis、Action、Verification、Report。

优先改动：

- `active_alerts > 0` 时“下一步诊断建议”应展示真实 Incident，并跳转 AI Ops。
- K8s `available=false` 时 KPI 变 warning，显示 `Agent / minikube 不可达`。
- 增加 Recent Incidents、Recent Deployments、Recent Benchmarks 三个低矮列表。

### 5.2 模型服务 Model Serving

当前优点：

- 已接真实 `/api/service-instances`。
- 能展示 AIBrix Gateway、auto-router、round-robin、vLLM replica。
- 行内 healthcheck 已有。

当前问题：

- 页面名是“模型服务监控”，但主表更像 endpoint 清单，治理策略不够突出。
- 实例 `unknown` 状态下仍计算出 `副本健康 2/2`。
- 缺少“模型版本 -> runtime -> replica -> GPU -> route strategy”的绑定关系。

建议新增：

- 模型服务生命周期：model version、runtime、serving engine、deployment mode、replica count、canary/stable、rollout status、SLO policy。
- Router Governance：primary strategy、fallback strategy、canary percentage、traffic split、retry、timeout、circuit breaker、rate limit、load shedding。
- Target Pod / Upstream Distribution：从 `metrics/current.target_pod_counts`、endpoint stats 派生。
- 详情抽屉增加：Basic Info、Routing Policy、Recent Metrics、Healthcheck Result、AI Diagnose。

### 5.3 Kubernetes

当前优点：

- 页面结构接近云原生控制面，已有 cluster overview、workload、diagnostic tabs。
- 工具栏具备 namespace、搜索、状态过滤。
- 行内可跳 AI Ops。

当前问题：

- 当前运行环境 `snapshot.available=false`，页面主体大量 skeleton，用户难以判断是“集群空”还是“采集失败”。
- 集群概览、GPU 调度、Autoscaling 仍有较多静态数据。
- Workload 行点击还没有详情抽屉。

建议：

- 当 `available=false` 时，在页面顶部显示 Agent 状态横幅，包含错误原因、Agent endpoint、重试按钮。
- Workload 表改成“真实数据优先”：Deployment / Pod / Event 均为空时显示错误态而不是 skeleton。
- 增加 Workload Detail Drawer：metadata、labels、containers、image、ready、restarts、events、related service instance、AI Diagnose。
- 增加 Node/GPU 视图：GPU model、allocated/free、memory、temperature、power、pending workloads。
- Autoscaling 区分真实 HPA/KEDA 与推荐扩缩容。

### 5.4 可观测性 Observability

当前优点：

- 已接 `/api/metrics/current`、history、requests。
- 已具备时间窗、endpoint/status 过滤、异常 trace 跳 AI Ops。
- Host 指标已能从 Agent 透传。

当前问题：

- 当前无请求流量时大量卡片显示绿色 `0`，不容易区分“系统健康”和“无样本”。
- GPU 当前接口返回空数组，但页面只显示“暂无 GPU 数据”，缺少数据源状态。
- 请求追踪面板在首屏下方，用户不容易从异常指标进入具体 trace。

建议：

- KPI 增加 sample count；样本数为 0 时整组标记为 neutral。
- 增加 Data Source Status：metrics、host、gpu、cadvisor、kubernetes、vLLM upstream。
- Trace 表格支持 request_id 复制、详情抽屉、payload/log preview。
- 趋势图与资源表统一使用全局时间窗组件。
- `diagnoseTrace()` 跳转 AI Ops 后，AI Ops 必须读取 query 并自动生成上下文卡。

### 5.5 AI Ops

当前优点：

- 页面已经表达 Incident、证据、RCA、Tool Calls、Remediation、Verification。
- 右侧 AI Ops Copilot 支持 SSE 会话的前端框架。

当前问题：

- 主页面数据仍是静态数组，没有接 `/api/incidents`。
- 右侧 Copilot 请求 `/api/aiops/*`，当前 Java 后端没有对应接口，截图中显示 benchmark 列表加载失败。
- Observability/Kubernetes 带 query 跳转后，AI Ops 没有消费上下文。
- 1180px 下右侧 Copilot 压缩主工作区，表格很挤。

建议：

- 第一阶段先接真实 Incident：`GET /api/incidents`、`GET /api/incidents/{id}`、ack、resolve。
- AI Ops 页面读取 `source=trace/workload/config` query，自动构造诊断上下文。
- 中间区域优先展示结构化报告：Problem Summary、Root Cause、Evidence、Impact、Actions、Confidence。
- Evidence 右侧面板绑定真实来源：metrics、traces、pods、configs、knowledge docs、benchmark。
- Action Plan 卡片必须包含 risk、expected impact、approval status、verification。
- Execute/Rollback 按钮默认 disabled 或 preview，不能误导为真实执行。

### 5.6 Knowledge / RAG

当前问题：

- 前端页面已完成基本文档列表、检索、新建、重建索引交互。
- 但当前 Java 后端没有 `/api/knowledge/*`，截图中直接 404。

建议：

- 短期：Java 后端添加 KnowledgeController，代理旧 Python RAG 或直接落库实现 lexical search。
- 中期：Knowledge 页面改成“AI Ops 证据治理中心”，不是普通文档管理。
- 增加 Corpus Overview：Runbooks、Kubernetes YAML、Config History、Incident Reports、Benchmark Reports、Service Docs。
- 增加 Index Status：document count、chunk count、embedding model、vector store、last build、retrieval latency。
- 增加 Evidence Usage：哪些诊断引用过该文档、覆盖了哪些 Incident 类型。

### 5.7 Benchmarks

当前问题：

- 页面展示的是静态 demo 指标，后端 Java 当前没有 `/api/benchmarks/*`。
- 启动 Benchmark 后才查询 run，但启动接口当前会失败。
- 页面没有 baseline/candidate 对比，门禁价值不够明确。

建议：

- Java 暴露统一控制面接口：create run、get run、events、report summary。
- Python benchmark worker 仍可执行实际压测，但由 Java 记录 run metadata、events、report。
- 页面增加 baseline vs candidate：
  - baseline version
  - candidate version
  - latency regression
  - throughput regression
  - TTFT/P95/P99 对比
  - cost per 1K tokens
  - GPU efficiency
  - release blocking reason
- 与 Pipelines 联动：Pipeline 中的 Benchmark Gate 点击进入对应 run。

### 5.8 Config Center

当前优点：

- 已接真实 `/api/config/items` 和 `/api/audit/events`。
- 新建配置、发布版本、回滚抽屉已具备基础交互。

当前问题：

- 截图中“新建配置”按钮背景失效，几乎不可见。
- 表格列数不匹配，`操作` 列换行到下一行。
- 缺少 Diff、影响服务、回滚预览和高风险确认。

建议：

- 立即修 CSS 列数和 `infra-action-btn` 背景。
- 版本抽屉增加 `active vs selected` Diff。
- 配置项表格增加 impacted services、risk level、last change reason、approval status。
- 回滚前弹出确认，展示影响范围与验证方式。
- 最近审计可作为 AI Ops Evidence 被引用。

### 5.9 Pipelines

当前优点：

- 已接真实 `/api/deployments`。
- 支持触发部署、finish、rollback 的基础交互。

当前问题：

- 表格列数不匹配，`操作` 列换行。
- 页面仍像部署记录表，CI/CD 自动化和发布门禁不明显。
- running 部署没有 timeline，也没有 SLO/Benchmark/Config/Model gate。

建议：

- 增加 Pipeline Run Timeline：checkout、build、scan、deploy、SLO check、benchmark gate、approval、rollback。
- 表格增加 commit id、image tag、config version、model version、benchmark run id。
- running 状态展示下一步 gate，而不是只显示“成功/失败”人工按钮。
- rollback 操作使用确认弹窗，并写审计。

### 5.10 Models / Registry

当前问题：

- 当前页面实际管理 serving instances，更像 Model Serving 的副本定位页。
- 模型注册表应表达模型版本、artifact、runtime compatibility、deployment binding。

建议：

- 将 Models 定位为模型治理中心：
  - model version lineage
  - artifact location
  - quantization type
  - context length
  - runtime profile
  - evaluation score
  - SLO profile
  - deployment binding
  - rollback target
  - owner / approval status
- 与 Model Serving 明确分工：
  - Model Serving 管 runtime、endpoint、router、SLO。
  - Models 管模型元数据、版本、artifact、上线门禁。

### 5.11 Demo Apps

当前问题：

- Demo Apps 用于验证业务接入是合理的，但页面视觉和内容仍像示例卡片。

建议：

- 明确 Demo Apps 是验证工作负载，不进入主闭环。
- 每个 Demo 展示：endpoint、RAG enabled、streaming enabled、last run、benchmark link、trace link。
- 提供“发送一次示例请求”和“进入 trace”入口，便于演示平台闭环。

### 5.12 Settings

当前问题：

- 设置页仍以静态展示为主。

建议：

- MVP 做只读平台设置：
  - API base URL
  - backend health
  - agent health
  - kubernetes available/error
  - gpu available
  - cadvisor configured
  - auth mode
  - audit enabled
- 写操作后续再做，并统一走审计和确认弹窗。

## 6. Storage / Metadata / Autoscaling 的处理建议

当前不建议立即新增一级菜单。先把三类能力显性化到现有页面：

### Storage

- Dashboard：Layered Storage 总览。
- Models：model store、artifact、PVC、object store。
- Knowledge：vector store、index、embedding。
- Observability：metric store、log store、trace store。

### Metadata

- Services：service metadata、owner、dependency、SLO。
- Models：model metadata、runtime binding、lineage。
- Config：config metadata、version、impact。
- Pipelines：deployment metadata、commit、image、artifact。

### Autoscaling

- Kubernetes：HPA、KEDA、GPU pending workloads。
- Model Serving：replica recommendation、queue-based scaling。
- Observability：TTFT、queue、GPU trigger signals。
- AI Ops：scale action plan。

只有当这些能力在多个页面重复且无法承载时，再新增独立页面。

## 7. 建议实施顺序

## 8. 验收标准

每次前端改造后建议至少检查：

- `npm run build` 通过。
- 1440px 和 1180px 两种截图不重叠、不横向撑破主布局。
- 右侧 Copilot 不遮挡主工作区。
- 表格宽字段在表格容器内滚动。
- 所有真实执行按钮都有 loading、disabled、error、toast。
- 高风险动作有确认弹窗。
- `unknown`、`unavailable`、`empty` 不被渲染成健康。
- 从 Observability/Kubernetes/Config 跳 AI Ops 时，上下文能被 AI Ops 页面消费。
