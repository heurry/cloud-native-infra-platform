# 09 后端开发计划

> 制定时间：2026-05-29
> 适用前提（已与负责人确认）：
> - **后端技术方向**：按本目录文档迁移到 **Spring Boot（模块化单体）+ Go Infra Agent**，Python 降级为 AI / RAG / Benchmark 工具链 worker。
> - **Kubernetes 数据源**：使用**实集群**（kubectl / client-go）采集，不依赖 mock / seed 数据。

## 1. 现状盘点（基于代码实查）

### 1.1 前端 `apps/web`（React + Vite + Tremor）— 页面已渲染，但交互完成度分三档

> 重要修正：前端**页面布局/视觉基本完成**，但**很多页面只是占位展示，并未实现对应的交互动作**（例如 Settings 没有任何可设置控件）。需区分"已渲染"与"交互已实现"。

按代码实查（统计各页 `api()` 调用、`onClick`、`useState`）分为三档：

| 档位 | 页面 | 现状 | 后续需要 |
| --- | --- | --- | --- |
| ✅ **真实接口已通** | ServicesPage、ModelsPage、ObservabilityPage、KnowledgePage、BenchmarksPage、AIOpsCopilotPanel | 有 `api()` 调用 + 交互（健康检查、检索、压测、SSE 聊天等） | 后端迁移时保持接口契约即可 |
| ⚠️ **仅本地交互 / mock 数据** | KubernetesPage（筛选、抽屉能动，但数据来自 `mockPlatformData.ts`）、PlatformOverviewPage（仅 `/api/metrics/current` 真实，K8s/incident 为 mock）、AIOpsPage 主页面（偏展示，聊天在 Copilot 面板内） | 无后端，数据写死 | 后端补接口 + 前端脱 mock |
| ❌ **纯静态占位** | **SettingsPage、ConfigCenterPage、PipelinesPage**（`onClick / useState / api` 计数全为 0） | 写死常量数组渲染，无表单、无输入、无保存动作 | **后端补接口 + 前端从零补交互**（表单、写操作、确认弹窗） |
| ⬜ **展示页（不补交互）** | **DemoAppsPage** | 设计上仅作示例展示 | 无需补交互，保持现状 |

结论：**后端补齐只是其中一半工作。占位页（Settings / Config / Pipelines）还需要前端实现交互动作**，否则即使后端接口就绪，页面仍不可用。计划需把"前端交互补全"和"后端接口/脱 mock"作为两条并行线。具体待补交互见 §7。

## 2. 目标形态

```text
React Console（保持 /api/* 契约不变）
  -> Spring Boot 模块化单体（控制面）
       gateway / metadata / model-serving / observability
       benchmark / config / ai-gateway / audit
  -> Go Infra Agent（实集群采集：Pod/Deployment/Service/Event + 节点/GPU）
  -> Python AI Worker（RAG 检索、SSE 聊天、Benchmark 执行）
  -> PostgreSQL（Flyway 管理，表结构对齐 05-database-design.md）
  -> Kubernetes + vLLM + AIBrix 运行时
```

迁移原则：**不抛弃 Python，而是新设 Java/Go 控制面，Python 退为被 Java 调用的工具 worker。**

## 3. 分阶段计划

### Phase 0 — 基础脚手架（最高优先）

1. 新建 `backend/` Spring Boot 模块化单体，按 02-arch §3.2 的 package 分层：
   `gateway / metadata / model-serving / observability / benchmark / config / ai-gateway / audit`。
2. 接入 **PostgreSQL + Flyway**，按 `05-database-design.md` 建全表；SQLite 中 `service_instances / request_traces / documents / benchmark_runs` 按相同列名平迁。
3. 新建 `agent/` Go Infra Agent 骨架：client-go 连接实集群，提供 `/healthz`、`/metrics`，向 Spring Boot 上报快照。
4. 前端把 `vite` 代理 / `VITE_API_BASE` 指向 Spring Boot（如 `:8080`），**保持 `/api/*` 路径不变**。

交付物：服务可启动、DB 迁移可执行、Go Agent 能连上集群并返回原始资源。

### Phase 1 — 只读闭环（优先让前端脱 mock）

- **Go Agent → Observability Service**：采集实集群 Pod/Deployment/Service/Event 落 `k8s_resources`/`k8s_events`，供 `GET /api/kubernetes/pods`、`/deployments`（→ KubernetesPage 脱 mock）。
- **Metadata + Model Serving Service**：迁移 `GET /api/service-instances`、`POST .../{id}/healthcheck` 到 Java。
- **Platform Overview 聚合**：新增 `GET /api/platform/overview`（health score / running services / alerts / k8s 摘要 / GPU / QPS·P95·TTFT / recent benchmarks / AI summary）→ Overview 脱 mock。
- **Metrics**：`/api/metrics/current|history|requests` 迁到 Java，GPU/host 经 Go Agent。

### Phase 2 — Config / Deployments + Audit + Incidents

> 注意：ConfigCenterPage / PipelinesPage 当前是**纯静态占位**，此阶段是"后端接口 + 前端交互"双线工作。

- 后端：`GET/POST /api/configs`、`POST /api/configs/{id}/versions`、active/inactive 切换、`deployments` 列表。
- **前端（占位页补交互）**：ConfigCenterPage 补"新建配置 / 新建版本 / 查看历史 / 标记 active"的表单与动作；PipelinesPage 补部署记录列表与详情交互。
- 后端：所有写操作记 `audit_events`（actor / action / resource），提供 `GET /api/audit-events`。
- 后端：最小实现 `incidents`/`incident_events`，让 Overview 的 Recent Incidents 用真实数据。

### Phase 3 — AI Gateway（Java 编排 × Python 工具）

- 新增结构化 `POST /api/ai/diagnose`（02-arch §4.2）：聚合 metrics / traces / pods / 配置变更 / benchmark / RAG 证据，调用 vLLM，返回 `Root Cause / Evidence / Impact / Recommended Actions / Confidence`。
- 现有 FastAPI `aiops.py`（SSE 聊天）、`rag/retriever.py` 保留为 **Python AI Worker**，由 Java 通过 HTTP 调用。
- `/v1/chat/completions` 路由、round-robin / auto-router 逻辑迁移到 Java Model Serving。

### Phase 4 — 切换、Settings 落地与观测强化

- Benchmark 拆为 Java（队列 / 状态）+ Python（执行）。
- FastAPI 原型缩减为 Worker 专用或停用。
- Go Agent DaemonSet 化，接 vLLM `/metrics`，SSE 指标流。
- **SettingsPage 落地**：当前为纯静态展示。按需选择：(a) 只读化为"系统信息/连接状态"页（最小成本）；(b) 做成可写配置（平台名称、默认语言、密钥脱敏管理等）+ 后端 `GET/PUT /api/settings`。建议 MVP 先做 (a)，可写项放后续。

## 8. 企业级前端待补的横切能力

> 前面 §7 是"每个页面的业务交互"，本节是"作为企业级应用必须具备、但当前整体缺失的横切（cross-cutting）能力"。
> 现状基线（代码实查）：`package.json` 仅有 `@tremor/react / lucide-react / tailwind` 等，**没有** react-router、数据请求库、状态管理、鉴权、i18n、测试框架、通知组件。

### 8.1 工程基础设施（最高优先，影响所有页面）

| 能力 | 当前现状 | 待补 |
| --- | --- | --- |
| **路由** | `App.tsx` 用 `?page=` 查询参数 + `useState` 伪切换 | 引入 `react-router`：真实 URL、深链、面包屑、`/services/:id` 详情路由、404、路由级懒加载 |
| **数据请求层** | `lib/api.ts` 薄 `fetch` 包装；各页 `useEffect+useState` 手写 | 引入 `@tanstack/react-query`：缓存、自动重试、失效刷新、loading/error 统一、并发去重 |
| **API 客户端** | 无 baseURL/鉴权头/超时/traceId/统一错误 | 统一 client：注入 `Authorization`、`x-request-id`、超时、401→跳登录、错误码→错误对象 |
| **全局状态** | 无 | 轻量 store（Zustand 等）放当前用户、权限、主题、通知 |
| **环境配置** | 同源硬编码 | `VITE_API_BASE` 等多环境（dev/staging/prod）配置 |

### 8.2 鉴权与权限（企业级硬性要求）

- **登录 / 登出 / 会话**：登录页、token 存储与刷新、过期跳转（当前完全没有）。
- **RBAC 权限门控**：按 `admin / sre / developer / viewer` 控制菜单可见性、按钮可用性（如"回滚""执行修复"仅 sre+）。Settings 里写死的 "RBAC Enabled" 要变成真实生效。
- **当前用户区**：顶栏头像、所属角色、租户/工作区切换。
- **高风险操作二次确认**：回滚、删除、扩缩容、生产配置变更统一走确认弹窗（部分页面 §7 已提到，这里统一成组件）。

### 8.3 反馈与健壮性（用户体验底座）

- **统一 Loading**：骨架屏 / spinner（当前多数页直接渲染或 catch 后塞 mock，用户分不清"真数据"还是"兜底假数据"——企业级里这点很危险，应明确区分）。
- **统一 Empty State**：无数据时的空状态插画 + 引导动作。
- **统一 Error State + ErrorBoundary**：页面级错误边界，避免单页崩溃白屏；接口失败给重试按钮而非静默塞 mock。
- **全局通知 Toast**：操作成功/失败提示（新建配置、healthcheck、回滚结果等），当前完全没有。
- **乐观更新与回滚**：写操作即时反馈 + 失败回退。

### 8.4 数据表与表单标准化（平台有大量表格/表单）

- **企业级 DataTable 统一能力**：服务端分页、排序、列筛选、列显隐/自定义列、行选择/批量操作、密度切换、CSV/JSON 导出。当前 `DataTable` 是静态渲染，KubernetesPage 的工具栏全是装饰。
- **表单体系**：引入 `react-hook-form + zod` 做校验、错误提示、提交态、脏检查（Config/Settings/Benchmark 创建都需要）。
- **筛选/查询持久化**：筛选条件写入 URL query，可分享、可刷新保留。

### 8.5 可观测性与实时性

- **SSE/WebSocket 统一封装**：指标流、AI Ops 流式诊断、Benchmark 事件流（后端已有 SSE，前端需统一重连/错误处理）。
- **前端遥测**：错误上报（Sentry 类）、性能埋点（页面加载/接口耗时）、用户行为埋点。
- **全局时间窗 & 自动刷新控制**：统一的时间范围选择器 + 刷新频率开关（Observability 已有局部，应抽成全局）。

### 8.6 国际化与可访问性

- **i18n**：当前中文硬编码，企业级常需中英双语（`react-i18next`），文案抽离。
- **可访问性 a11y**：键盘导航、focus 管理、aria 标签、对比度（抽屉/弹窗尤其需要）。
- **主题**：浅色为主已具备，按需补深色局部面板/暗色模式开关（文档 02-arch 提到深色局部组件）。

### 8.7 设计系统与一致性

- 把 `PlatformPrimitives / PlatformPanels` 沉淀为**正式组件库**（抽屉 Drawer、确认 Modal、Toast、Tag、Pagination、Filter 统一规范，对齐 `修改建议2.md` 的"五层结构 + 统一抽屉/弹窗规则"）。
- 统一图表封装（折线/环形/柱状/进度条/拓扑），目前各页各写。

### 8.8 质量保障

- **测试**：当前 0 测试。补 Vitest 单测（工具函数/hooks）、React Testing Library 组件测试、Playwright E2E（覆盖 §6 演示链路）。
- **CI/Lint**：ESLint + Prettier + type-check + build 在 CI 卡口。
- **Storybook**（可选）：组件库可视化与回归。

### 8.9 优先级建议

| **P0** | react-router + react-query + 统一 API client + Loading/Error/Empty + ErrorBoundary + Toast | 是所有页面脱 mock 和交互补全的地基，越早越省返工 |

> 关键提醒：**§8.1 的地基（路由/请求层/统一反馈）应当先于或并行于 §7 的页面交互补全**。否则每个页面都会各写一套 loading/error/请求逻辑，后期统一成本很高。
